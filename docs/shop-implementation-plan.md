# 상점 개편 구현 계획

작성일: 2026-09-07  
상태: **로컬 구현 완료 / 운영 SQL 적용·배포 전**  
기획 기준: [상점 아이템](shop-items.md)

## 1. 구현 목표와 범위

생활관은 병사 충원, 체단실은 직접 클릭 강화, P.X는 병사 강화, 행정반은 휴가 누적, 위병소는 선물·공유·기념품으로 역할을 나눈다. 병사는 메인 버튼에 실제로 손을 대는 캐릭터로 표현한다.

기획에 따른 구현과 로컬 검증을 마쳤다. 아래 체크리스트는 실제 확인한 범위를 표시하며 운영 적용은 별도로 남겨 둔다.

- 메인에 따로 있는 **일수 선물하기 버튼을 위병소 행동 카드로 이동**한다.
- 기존 Vanilla HTML/CSS/JavaScript와 Supabase를 사용한다. 프레임워크·번들러·애니메이션 라이브러리는 추가하지 않는다.
- 직접 클릭·자동 클릭·광고 보상·선물·휴가의 회계를 분리한다. 기존 입대일·전역일 계산과 리더보드의 순누적 정의를 유지한다.
- 비로그인 플레이와 비로그인 선물 수령을 유지한다. 선물 발신은 기존대로 로그인 필요.
- 가격과 성장 속도는 기획안의 초깃값으로 구현한 뒤 실제 진행 시간을 측정해 조정한다.
- 기존 구매 기록을 삭제하거나 기존 유저에게 새 게임 시작을 요구하지 않는다.

## 2. 착수 시 확인한 변경 지점

## 3. 구현 기본안

### 3.1 아이템 데이터

- 기존 `id/name/price/category/description/effect` 구조를 유지한다.
- 판매 목록 `items`와 판매 종료한 정의 `legacyItems`를 같은 JSON에 둔다. 판매 필터는 전자만, 기존 보유 조회는 둘 다 읽는다. 양쪽을 합쳐도 ID가 중복되지 않아야 한다.
- 기존 이병·일병·상병·병장 ID는 유지한다. 분대장 상병과 말년 병장은 새 ID를 부여한다.
- 의미가 바뀌는 구음식의 ID를 새 효과로 덮어쓰지 않는다. 예를 들어 구 냉동 피자 ×5는 구정의로 남기고 속도 강화 냉동 피자는 새 ID로 만든다.
- 신규 효과는 `manual_add`, `crew_power`, `crew_speed`, `leave`로 구분하고 기존 `auto/share`를 재사용한다. 속도 값은 %p, 휴가 값은 종류와 확정 일수다.
- 선물 카드는 `action: "gift"`로 구분한다. 가격 0인 구매 아이템으로 처리하지 않으며 보유 목록에 넣지 않는다.
- 구매 전에 데이터의 효과 타입·양의 간격·정수 가격·휴가 종류·추가치 범위를 검증한다. 서버 휴가 가격표도 같은 버전과 값인지 테스트한다.
- 새 판매 구성은 병사 6 + 운동 4 + 음식 5 + 휴가 3 + 위병소 5 = **23개 카드**다. 이 중 소문내기·선물하기는 일반 영구 구매가 아니다.

### 3.2 직접·자동 계산

기획의 공식을 작은 순수 함수로 분리하고 화면 표시와 지급이 같은 결과를 사용하게 한다.

| 계산 | 기본 규칙 |
| --- | --- |
| 직접 1회 | (1 + 운동 추가치 합계) × 공유 배수 |
| 병사 1회 | (1 + 음식 삭제량 추가치 합계) × 공유 배수 |
| 병사 간격 | 기본 간격 ÷ (1 + 음식 속도 %p 합계 / 100) |
| 자동 일/초 표시 | 각 병사의 1회 삭제량 ÷ 실제 간격(초)의 합계 |
| 휴가 | 구매 영수증의 종류별 일수 합계 |
| 광고·선물 | 고정 보상 또는 입력한 일수, 생산 배수 미적용 |

`renderWallet()`, 직접 클릭 핸들러, `pop()`, `autoTick()`, `settleOffline()`까지 모든 기존 multiplier 호출을 점검한다. 직접 클릭은 계산한 값을 한 번 지급하고 같은 숫자를 표시한다. 총합 표시는 정수, 초당 속도는 표시용 소수다.

타이머는 구매·계정 복원·속도 변화·광고 종료 시에만 필요한 부분을 재구성한다. 지갑이 바뀔 때마다 병사 DOM과 타이머를 다시 만들지 않는다. 광고 재생 중에는 생산과 연출을 함께 멈추며 재개 시 광고 시간을 소급 지급하지 않는다.

### 3.3 기존 구매자의 효과 보존

현금성 환불이나 누적 삭제 일수 보상을 새로 만들지 않고 **구매한 구효과를 보존하는 방식**을 기본안으로 채택한다.

- 구배수·짬은 신규 판매에서 숨기고 ‘기존 구매 효과’로만 계산한다. 공유를 제외한 구배수 최댓값을 L이라 할 때 직접 삭제량과 신규 병사 삭제량의 기본값은 각각 `max(새 기본값, L)`로 한다. 이후 공유 ×3을 한 번 적용한다.
- 하사·중사·상사·연병장 자동 아이템은 예전 간격과 L에 따른 생산을 유지한다. 신규 음식 속도는 새 병사 6종에만 적용한다. 구자동 생산은 ‘이전 부대 지원’ 요약에 표시해 신규 병사 6명 배치를 침범하지 않는다.
- 공통 계급 4종은 기존 간격을 유지한다. 신규 가격은 기존 보유자에게 재청구하지 않는다.
- 구기념품은 보유 기록에 남긴다. 지니티비 등 효과가 있던 물건을 장식만 남기고 무효화하지 않는다.
- 구 위로휴가 일주일은 7일로 한 번 인정한다. 로컬 재실행·재로그인·여러 기기에서도 중복되지 않는 이관 키를 쓴다. 서버는 구아이템 보유 여부를 확인한다.
- 구룰렛의 과거 결과는 이미 잔액에 반영되어 있으므로 다시 지급하지 않는다.
- 국방부 시계는 구보유자의 8시간 한도를 유지한다. 신규 판매는 이번 범위에 넣지 않는다.
- 오프라인 계산은 떠날 때의 생산 조건으로 정산한다. 공유가 만료되는 구간은 만료 전후로 나눠 실제 클릭 횟수만 계산한다. 이석 중 새로 산 효과를 과거 시간에 소급 적용하지 않는다.
- 이관 전에 입력 상태를 보존하고, 실패하면 구매를 잠시 막은 채 재시도 안내를 보여준다. 상태를 초기화하거나 부분 이관을 완료로 표시하지 않는다.

이 방식에서는 기존 고배수 보유자의 초반 강화 체감이 낮을 수 있다. 데이터 보존을 우선하는 의도된 차이이며, 신규 사용자 밸런스와 따로 검증한다.

### 3.4 휴가 저장·재구매

**종류별 숫자만 max 병합하지 않는다.** 두 기기에서 각각 연가 1일을 샀는데 max(1, 1)로 합치면 한 구매가 사라진다. 비용과 지급량을 함께 가진 구매 영수증을 기준으로 합산한다.

- 각 구매는 고유 operation ID, 상품 ID, 가격표 버전, 가격, 종류, 지급 일수로 표현한다. 같은 ID의 재전송은 한 구매로 취급한다.
- 비로그인 구매도 로컬에 영수증 한 건을 저장한다. 저장 성공 후에만 구매 완료를 표시한다. 저장 실패 시 비용과 휴가 모두 변하지 않는다.
- 휴가 비용은 영수증에서 계산하고 기존 `ad.spent`에 다시 더하지 않는다. **유효 사용액 = 기존 spent + 휴가 영수증의 비용 합계**, 잔액은 `max(0, total + gifted - 유효 사용액)`이다. 이중 차감을 막기 위한 구분이며 화면에는 하나의 잔액만 보인다.
- 순누적은 기존 `max(0, total + gifted - gsent)`를 유지한다. 선물 발신은 기존 spent·gsent, 수령은 gifted로 기록한다.
- `balance()`를 사용하는 상점·선물·광고 안내와, 저장값을 직접 읽는 분석 경로에도 유효 사용액 정의를 적용한다.
- 로컬 영수증은 ID별 키에 기록해 전체 배열 덮어쓰기로 다른 탭의 구매가 사라지지 않게 한다. 모든 새 클라이언트의 구매·선물 발신은 같은 쓰기 잠금을 사용해 잔액 확인과 지출 반영을 직렬화한다. 잠금을 사용할 수 없는 환경은 단일 탭 구매로 제한하고 안내한다.
- 로컬 영수증의 계정 소유와 동기화 완료 여부를 구분한다. 익명 영수증은 최초 연결 계정에만 귀속시키며 계정 전환 시 다른 계정으로 재수입하지 않는다. 로그아웃·계정 변경 중인 요청의 결과도 원래 계정으로만 반영한다.

서버에는 `leave_purchases`와 영수증 동기화 RPC를 `board.sql` 안에 추가한다. operation ID의 고유 제약, 본인 조회 RLS, 직접 DML 차단을 둔다. 서버가 상품 ID·버전으로 가격과 지급량을 결정하며 클라이언트가 보낸 숫자를 그대로 신뢰하지 않는다. 동일 ID·동일 내용은 멱등 성공, 다른 내용이나 타 계정 소유 ID는 거부한다.

기존 6인자 `sync_my_record`는 유지한다. 영수증은 별도 RPC로 제한된 개수씩 동기화하고 성공 응답 전에 동기화 완료로 표시하지 않는다. 응답 유실 후 재시도해도 영수증 비용과 휴가는 한 번만 집계한다. 계정 복원은 기존 지갑과 영수증을 모두 읽은 뒤 구매를 활성화한다. 전체 영수증 조회는 페이지 단위로 누락 없이 처리하며 과거 가격을 현재 가격으로 재계산하지 않는다.

**정확성의 범위:** 새 휴가 영수증의 중복·유실은 방지하지만, 기존 지갑은 클라이언트 수치와 max 병합에 의존한다. 서로 다른 기기의 오프라인 동시 지출이나 이미 열려 있는 구버전 탭까지 서버가 원자적으로 차단하지는 못한다. 전체 지갑을 서버 거래 원장으로 바꾸는 작업은 이번 범위 밖이다. 구버전으로 플레이하지 않도록 갱신 안내를 제공하고 이 한계를 테스트 결과와 구분해 기록한다.

### 3.5 위병소 선물 동선

1. 상점의 위병소 첫 카드가 `일수 선물하기`다. 전체 목록과 검색에서도 찾을 수 있다.
2. 기존 메인의 버튼은 제거한다. 카드 클릭은 상점 컨테이너의 이벤트 위임으로 받으며 아이템 구매 함수에 흘리지 않는다.
3. 상점을 닫고 기존 선물 창을 연다. 상점에서 시작한 발신인지 외부 링크 수령인지 복귀 경로를 기억한다.
4. 발신 창을 닫으면 위병소로 돌아온다. ‘전체/검색’에서 진입했더라도 도착지는 위병소로 통일하고 검색어를 비운 뒤 선물 카드가 보이도록 스크롤·포커스를 맞춘다.
5. 구글 로그인 리디렉션 전에 선물 작성으로 돌아갈 의도만 sessionStorage에 저장하고, 인증 완료 후 한 번 소비한다. 편지 내용이나 선물 토큰을 로그인 복귀 상태·분석 이벤트에 넣지 않는다.
6. `?gift=` 유입은 기존 `openClaim()`을 직접 연다. 수령 닫기와 900ms 자동 닫기는 메인 상점 버튼으로 복귀하며 위병소로 강제 이동하지 않는다.
7. 닫기·Esc·배경 클릭·완료 후 닫기가 같은 복귀 처리를 사용한다. 모달 전환 중 메인 inert와 포커스가 어긋나지 않게 하고 키보드 포커스가 현재 모달 안에 머물게 한다.
8. 이번 세션에 생성한 링크는 창을 닫았다 다시 열어도 확인할 수 있게 한다. 새 선물 만들기를 선택할 때 초기화한다. 새로고침 후 발신 내역함은 추가하지 않는다.

발신 금액은 정수 1~1,000,000일 및 현재 잔액 이하, 편지는 기존 200자 제한을 맞춘다. 전송 중 중복 실행을 막고 서버 생성 성공 후에만 차감한다. 실패한 요청을 자동으로 재전송해 선물을 두 개 만드는 방식은 쓰지 않는다. 기존 수령의 토큰당 1회 조건과 사용자 메시지를 textContent로 표시하는 처리는 유지한다.

선물 링크 생성 직후 응답 유실·브라우저 종료까지 정확히 복구하는 기능은 현재 RPC가 보장하지 않는다. 이번 버튼 이동으로 이 보장이 생겼다고 주장하지 않는다.

### 3.6 병사 디자인·애니메이션

- 기존 인라인 계급장 SVG를 확장하는 방향으로, 몸·팔·소품을 분리한 단순 SVG 캐릭터와 CSS transform을 사용한다.
- 먼저 이병과 누워 있는 병장 2종으로 375px에서 실루엣·손 접촉·중앙 버튼 터치를 검증한다. 그 결과를 나머지 4종에 적용한다.
- 캐릭터마다 대기·준비·접촉·복귀 포즈와 소품을 제작한다. 기획의 300~450ms 범위 안에서 신병은 신중하게, 말년은 짧게 움직이게 한다.
- 경제 계산이 기준이다. 타이머 지급 시점에 손 접촉과 숫자를 표시한 뒤 캐릭터별로 복귀하며, animationend 이벤트로 지급을 결정하지 않는다.
- 동시 동작은 2개까지만 표시하고 나머지는 숫자로 합산한다. 상점·광고·백그라운드에서는 장식 연출을 멈추고 밀린 애니메이션을 재생하지 않는다.
- 음식 전달, 운동 강화, 휴가 도장, 충원 등장 연출을 각각 한 번만 실행한다.
- 모바일 위·아래 3명씩 / 데스크톱 좌우 3명씩 배치. 44px 이상 조작 영역, 이름·현재 능력치 상세, 밝은/어두운 테마를 제공한다.
- 동작 줄이기 설정을 저장하고 OS 설정도 존중한다. 자동 동작의 소리·햅틱·직접 클릭 콤보는 끈다.
- 캐릭터 6종과 두 화면 배치의 실제 캡처를 남겨 최종 디자인을 검토한다. 기획의 문자 배치를 완성 디자인 검증으로 간주하지 않는다.

실행 명령은 `npm test`, `git diff --check`, 인라인 스크립트 `node --check`다. package.json의 모듈 타입을 바꿔 기존 경고만 없애려 하지 않는다. CommonJS 운영 스크립트에 영향을 줄 수 있다.

SQL은 격리된 Supabase 테스트 환경에서 `board.sql → gift.sql → board_test.sql → gift_test.sql` 순으로 검증한다. 기존 board_test는 인증 사용자 3명, gift_test는 1명 이상을 요구하므로 테스트 계정을 준비한다. 롤백 스크립트여도 운영 계정을 사용한 실행을 로컬 테스트로 표현하지 않는다.

### 수동 QA·밸런스

- 375px 모바일 Safari, 모바일 Chrome, 데스크톱 키보드에서 다섯 장소와 전체/검색을 확인한다.
- 선물 창의 금액·편지 입력 시 키보드 확대/가림, 뒤로 가기·Esc·로그인 실패·네트워크 실패를 확인한다.
- 비로그인 외부 수령, 이미 수령한 링크, 없는 링크를 확인한다. 테스트용 선물만 사용한다.
- 여섯 병사를 모두 보유한 상태에서 직접 연타해도 중앙 버튼을 누를 수 있고 손 접촉이 구분되는지 확인한다.
- 음식 구매로 실제 자동 간격이 짧아지는지, 운동으로 직접 지급량만 오르는지 확인한다.
- 동작 줄이기·음소거·백그라운드·광고 재생 후 복귀를 확인한다.
- 신규 / 구아이템 다수 보유 / 익명 후 로그인 / 계정 전환 / 두 탭 / 두 기기 프로필로 복원한다.
- 초당 직접 클릭 1회·3회와 방치 플레이에서 첫 운동, 첫 병사, 첫 음식, 첫 연가, 전 아이템까지 걸리는 시간을 기록한다. 테스트 전 가격을 확정 밸런스로 표현하지 않는다.
- 서버의 기존 허용치 200일/초 + 초기 여유분을 신규 최대 생산·구효과·8시간 정산과 비교한다. 정상 기록이 거절되면 계산 근거와 SQL 테스트를 함께 바꾼다.

## 6. 적용·실패 복구

1. 로컬 구현과 검증을 마친 뒤 변경 파일, 캐릭터 캡처, 테스트 결과, SQL 차이를 검토 가능한 상태로 정리한다.
2. 휴가 테이블/RPC는 기존 6인자 동기화를 유지하는 추가 변경으로 먼저 적용한다. 기존 gift RPC 권한·일회성 조건은 유지한다.
3. 테스트 계정으로 새 영수증의 저장·재시도·복원을 확인한 후 새 HTML과 items.json을 같은 배포로 적용한다.
4. 데이터 버전 불일치 시 구매를 활성화하지 않고 새로고침 안내를 한다. 옛 HTML과 새 아이템 정의의 혼합을 테스트한다.
5. 새 서버가 준비되지 않았거나 계정의 휴가 비용을 불러오지 못하면 로그인 사용자의 지출을 막고 복원 재시도를 제공한다. 누락된 비용을 0으로 간주해 구매시키지 않는다.
6. 장애 시 새 구매를 잠시 중단하는 호환 버전으로 되돌린다. 휴가 영수증을 모르는 구HTML로 단순 롤백하면 잔액이 부풀 수 있으므로 사용하지 않는다. 영수증과 이관 기록은 삭제하지 않는다.
7. 커밋·푸시·실서비스 SQL 적용·배포는 계획 수립과 별도 실행이다. 특히 main은 자동 배포 브랜치이므로 명시적 실행 권한을 확인한다.

### 저장과 복구의 실제 경계

- 휴가 구매는 영수증 한 건을 원자적으로 기록하고 비용을 한 번만 차감한다. 같은 operation ID 재전송은 중복 지급하지 않는다.
- 로그아웃 후에도 남는 지갑의 휴가 비용은 원래 계정에 귀속된다. 다른 계정 로그인에 재수입하지 않는다.
- 다른 탭의 지갑 소유자 변경은 기존 탭을 다시 불러오게 한다. 계정 전환 시 이전 오프라인 스냅샷과 공유 버프는 새 계정에 적용하지 않는다.
- 기존 일반 지갑의 여러 기기 동시 사용은 기존 max 병합 방식을 유지한다. 휴가 영수증 합집합 외의 전체 지갑을 서버 거래 원장으로 바꾼 것은 아니다.
- Web Locks 지원 브라우저는 지출 잠금을 공유한다. 미지원 브라우저의 localStorage 임시 임대는 단일 탭 사용을 유도하는 보조 장치이며 서버 트랜잭션 수준의 잠금은 아니다.
- 기존 선물 RPC의 생성 직후 응답 유실·브라우저 종료 복구 보장은 이번 변경 범위 밖이다.
