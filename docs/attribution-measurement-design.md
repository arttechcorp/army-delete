# 유입 출처·확산 측정 설계

이 문서는 "어느 커뮤니티 게시판이 사람을 데려왔고, 그 사람들이 얼마나 퍼뜨렸는가"를 어떻게 재는지 정의한다. 몇 달 뒤 대시보드 숫자를 다시 볼 때 정의를 재추론하지 않아도 되게 하는 것이 목적이다.

작성일 2026-09-08 · 최초 배포일 2026-09-08

관련 코드: `scripts/share.js`, `scripts/utm.js`, `index.html` head 스크립트, `scripts/posthog-setup.js`, `admin.html`

---

## 1. 왜 만들었나

배포 전까지 게시판별 성과를 비교할 방법이 없었다. 원인은 두 가지였다.

첫째, PostHog는 `utm_*` 파라미터를 **그 파라미터가 URL에 있던 `$pageview` 이벤트에만** 붙인다. 그래서 `first_delete_click`, `click_milestone_reached`, `session_engagement` 같은 실제 행동 이벤트에는 유입 출처가 아예 실리지 않았고, "어느 게시판 사람들이 실제로 버튼을 누르는가"를 물을 수 없었다.

둘째, 공유 링크가 유입 UTM을 그대로 퍼뜨리고 있었다. `shareLink()`가 `location.href`를 그대로 공유해서, 육군 게시판에서 들어온 사람이 공유하면 받는 사람도 육군 게시판 유입으로 집계됐다. 바이럴 분자가 자기 분모에 섞여 들어가 확산 계수가 무의미해졌다.

---

## 2. 측정의 토대 — 모든 이벤트에 실리는 4개 속성

브라우저마다 최초 방문 시 한 번 판정해 `posthog.register_once()`로 고정한다. 이후 **모든 이벤트에 자동으로 실린다.**

| 속성 | 값의 예 | 답하는 질문 |
|---|---|---|
| `first_source` | `dcinside`, `everytime`, `gundori`, `gomsin_cafe`, `user_share`, `direct` | 이 사람은 어떻게 들어왔나 |
| `root_source` | `dcinside` | 이 사람이 속한 확산이 시작된 게시판 |
| `root_content` | `army_post01`, `hongik_univ_post02` | 어느 글이 데려왔나 |
| `generation` | `0`, `1`, `2` … | 원조로부터 몇 다리 건넜나 |

### 핵심: `first_source`와 `root_source`는 다를 수 있다

공유로 들어온 사람은 `first_source = user_share`지만 `root_source = dcinside`가 유지된다. 그래서 육군 게시판이 만든 확산의 일부로 계속 집계된다. 이 분리가 없으면 "육군 게시판에서 시작된 확산"을 셀 수 없다.

`generation`은 이 사슬의 깊이다.

- `0` — 게시판 UTM 링크로 직접 유입
- `1` — 0세대가 만든 링크로 유입 (**직접 데려온 사람**)
- `2` 이상 — 간접 확산

### 왜 person property가 아니라 event property인가

이 서비스는 사용자 대부분이 비로그인이다. person property는 `identify()`가 도는 로그인 사용자만 채워지므로, 그걸로 집계하면 익명 사용자가 통째로 빠진다. 기존 코호트 정의(`scripts/posthog-setup.js`의 `behavioral()`)도 같은 이유로 이벤트 기반이다.

### 최초 유입 고정 (first touch)

`ad.attr`에 이미 저장된 유입이 있으면 **덮어쓰지 않는다.** 같은 사람이 나중에 다른 경로로 다시 들어와도 최초 출처가 유지된다. 저장과 주소 정리는 PostHog가 꺼진 환경에서도 동작한다 — 분석 기능이 아니라 앱 동작이기 때문이다.

## 3. 이벤트 지도 — 누가 찍는지가 중요하다

| 이벤트 | 찍는 주체 | 시점 |
|---|---|---|
| `share_link_created` | 보내는 사람 | 공유창을 띄우거나 링크를 복사할 때 |
| `gift_created` | 보내는 사람 | 선물 토큰이 만들어질 때 |
| `referral_landed` | 받는 사람 | 공유 링크로 들어왔을 때 |
| `gift_link_opened` | 받는 사람 | 선물 링크를 열었을 때 |
| `gift_claimed` | 받는 사람 | 수령 버튼을 눌러 서버가 성공을 돌려줬을 때 |

### 보내는 사람과 받는 사람은 퍼널로 묶을 수 없다

PostHog 퍼널은 **같은 person이 순서대로 밟은 단계**를 센다. `share_link_created → referral_landed`를 퍼널로 만들면 두 이벤트의 주체가 서로 다른 사람이라 항상 0%가 나온다.

그래서 이 쌍은 **두 개의 별도 계열**로 나란히 놓고 비율을 눈으로 읽는다(인사이트 ⑫). 반면 `gift_link_opened → gift_claimed`는 둘 다 받는 사람이라 진짜 퍼널이 성립한다(인사이트 ⑭).

## 4. 링크 규격

### 게시판 링크 (운영자가 `admin.html`에서 생성)

표준 UTM을 쓴다. 손으로 적지 말고 반드시 생성기를 쓴다 — `utm_content` 오타 하나면 집계가 조용히 두 소스로 갈라진다.

| 게시 위치 | `utm_source` | `utm_medium` | `utm_content` |
|---|---|---|---|
| 디시 육군 | `dcinside` | `community` | `army_post01` |
| 디시 해군 | `dcinside` | `community` | `navy_post01` |
| 디시 공군 | `dcinside` | `community` | `airforce_post01` |
| 에타 특정 학교 | `everytime` | `community` | `학교코드_post01` |
| 군돌이 | `gundori` | `community` | `게시판코드_post01` |
| 곰신카페 특정 카페 | `gomsin_cafe` | `community` | `카페코드_post01` |

`utm_campaign`은 `launch_202609`로 공통. 같은 게시판에 다시 올리면 `post02`, `post03`으로 회차를 올린다.

코드는 영문·숫자·언더스코어만 쓴다. 한글을 넣으면 생성기가 거부한다 — 조용히 뭉개면 `홍익대A`와 `서울대A`가 둘 다 `a`로 축약되어 서로 다른 학교가 한 소스로 합쳐지기 때문이다.

### 공유 링크 (사용자가 앱에서 생성)

```
https://도메인/?sid=dcinside.army_post01.a3f9.1
                  │        │           │    └ generation
                  │        │           └ 공유자 4자리 id (ad.sid)
                  │        └ 원조 utm_content
                  └ 원조 utm_source
```

받는 브라우저가 이 문자열만으로 출처를 복원한다. 서버 조회가 없다.

- 공유자 id는 브라우저마다 **고정**이다. 공유할 때마다 새로 만들면 "한 사람이 몇 명을 데려왔나"를 셀 수 없다.
- `generation`은 공유자의 세대 + 1이다.
- 선물 링크는 `?gift=토큰&sid=...` 형태로 둘 다 싣는다.
- 랜딩 후 주소창에서 `sid`와 `utm_*`는 지우고 **`gift` 토큰은 남긴다.** 수령 전에 지우면 새로고침에 선물이 사라진다.

### 자기 유입 배제

들어온 `sid`의 공유자 id가 내 `ad.sid`와 같으면 무시한다. 자기 링크를 눌러 돌아오는 것으로 확산 계수가 부풀지 않게 하기 위함이다.

## 5. 대시보드 인사이트와 판단 기준

대시보드: `군생활 삭제 — 코어 분석` (PostHog 프로젝트 595220, 대시보드 2067781)

| 번호 | 이름 | 무엇을 보고 무엇을 결정하나 |
|---|---|---|
| ⑨ | 게시판별 신규 유입 | `generation = 0`만 센다. 모든 비율의 분모 |
| ⑩ | 게시판별 핵심 행동 퍼널 | **유입 수가 아니라 이걸로 게시판을 판단한다** |
| ⑪ | 확산 세대 분포 | `1`이 없으면 바이럴이 전혀 없다는 뜻 |
| ⑫ | 공유 생성 vs 공유 유입 | 만들어진 링크 대비 실제 유입 (퍼널 아님) |
| ⑬ | 선물 발송 퍼널 | 만들어놓고 안 보내는 이탈 |
| ⑭ | 선물 수령 퍼널 | 열어놓고 안 받는 이탈 |
| ⑮ | 게시판별 확산 계수 | HogQL. `direct / seeded` |

### ⑩이 가장 중요하다

디시가 1,000명을 데려왔는데 첫 클릭이 15%고, 에타가 200명에 60%라면 다음 글은 에타에 써야 한다. 유입 수만 보면 정확히 반대 결론이 나온다. 이 분해가 이번 작업 전까지 불가능했다.

### ⑪은 가장 잔인하고 정직하다

`generation` 분포에 `0`만 있고 `1`이 없으면 공유가 아예 작동하지 않은 것이다. 링크 문구, 공유 버튼 노출 위치, 공유 보상을 의심해야 한다. `2` 이상이 나오기 시작하면 그때부터 진짜 확산이다.

### ⑭는 이번에 새로 보이게 된 구간이다

기존 `gift_claimed`는 수령 버튼을 눌러 **서버가 성공을 돌려준 뒤에만** 찍혔다. 그래서 선물 링크를 열고 그냥 나간 사람이 통째로 안 보였다. `gift_link_opened`가 그 분모다. 바이럴이 샐 가능성이 가장 높은 지점이다.

## 6. 측정되지 않는 것

> 이 절은 숫자를 해석할 때마다 다시 읽어야 한다. 한계를 모르고 보면 잘못된 결정을 내린다.

### ⑮는 엄밀한 K₇이 아니다

⑮의 `k_direct`는 조회 기간(최근 30일) 전체를 뭉뚱그린 누적 `direct / seeded` 비율이다. "각 사용자가 유입된 시점부터 7일 창"을 재는 K₇과 다르다. 세대별 유입 시점이 서로 다른데도 같은 기준일로 잘라서, 초기에는 과소, 후기에는 과대로 나올 수 있다.

엄밀한 K₇을 내려면 `share_id`에 박힌 공유자 코드로 보낸 사람의 최초 등장 시각을 찾아 수신 시각과 비교해야 한다. 데이터가 쌓인 뒤 실제 값으로 검증하며 붙일 항목이다.

### 분모가 과소 계상된다

게시판 글을 보고 링크 대신 검색해서 들어온 사람은 `direct`로 빠진다. 즉 `generation = 0`이 실제보다 적게 잡히고, **확산 계수는 실제보다 높게 나온다.** 절대값보다 게시판 간 비교에 쓴다.

### 사람이 아니라 브라우저를 센다

폰에서 보고 PC에서 다시 들어오면 두 명이다. 시크릿 모드, 사이트 데이터 삭제, 다른 브라우저도 각각 새 사람이 된다.

### `share_link_created`는 "공유함"이 아니다

브라우저는 실제 전송 여부를 알려주지 않는다. 공유 시트를 띄웠거나 링크를 복사한 시점까지만 확인 가능하다. 상점 공유 부스트가 원래 그 전제로 만들어져 있었고, 계측도 같은 한계를 물려받는다.

### 배포 이전 이벤트에는 이 속성들이 없다

배포 시점 이전 이벤트는 `root_source`가 비어 있다. HogQL에서 `null != 'direct'`가 참으로 평가되므로, ⑮ 쿼리는 `root_content`가 비어 있지 않은 행만 세도록 명시적으로 걸러낸다. 새 쿼리를 짤 때도 같은 가드가 필요하다.

## 7. 운영 절차

### 게시판에 글을 올릴 때

1. `/admin.html`을 열고 비밀번호를 입력한다.
2. 채널을 고르고 필요하면 코드(학교/게시판/카페)를 입력한다. 회차는 같은 게시판에 다시 올릴 때마다 올린다.
3. 생성된 링크를 복사한다. 복사한 링크는 페이지 하단 기록에 남는다 — **이 기록은 그 브라우저에만 저장된다.**

### 배포 직후 확인 순서

1. 실제 게시판 링크 하나를 브라우저에서 열고, PostHog Activity에서 `$pageview`에 `root_source`, `root_content`, `generation`이 실렸는지 본다.
2. 공유 버튼을 눌러 만들어진 링크에 `?sid=`가 붙는지, 그리고 그 안의 원조 출처가 맞는지 확인한다.
3. 다른 브라우저(또는 시크릿 창)에서 그 링크를 열고 `referral_landed`가 찍히는지 본다.
4. ⑪ 확산 세대 분포에 `1`이 나타나는지 확인한다.

### 정기적으로 볼 것

- 매일: ⑨(어느 글이 데려오나), ⑩(그 사람들이 실제로 쓰나)
- 주간: ⑪(확산이 일어나는가), ⑮(게시판별 확산 계수)
- 선물 기능을 밀 때: ⑬⑭

## 8. 남은 작업

| 항목 | 조건 |
|---|---|
| 엄밀한 K₇ 쿼리 | 유입 데이터가 며칠 쌓여 검증 가능해진 뒤 |
| 코호트 임계값 튜닝 | 실제 분포를 보고 |
| `utm_campaign` 회차 관리 | 다음 캠페인 시작 시 `launch_202609` 갱신 |

`npm run posthog:setup`을 다시 돌리면 인사이트 전부가 "갱신"으로 찍힌다. PostHog가 저장 시 쿼리 객체를 정규화해서 비교가 항상 어긋나기 때문이다. 정의는 스크립트가 단일 진실 원천이라 결과는 같지만, **PostHog UI에서 손으로 고친 인사이트는 다음 실행에 덮어쓰인다.**
